Real Estate Marketplace

A national-scale public listings marketplace — search-heavy, media-heavy, SEO-critical. This document defines the v1 requirements and the architecture that carries them to scale.

● v1 in progress Segment · Listings marketplace Next.js 16 · App Router Updated 2026-08-18

01 Product & Scope

A public listings marketplace in the Zillow / Rightmove class. Seekers search and discover; agents publish listings and receive leads. Target scale: millions of active listings, millions of daily visitors, heavy search/media load and traffic spikes.

v1 · in Shipping

  • Seeker search + map, filters, faceting, sorting
  • Listing detail — gallery, tour, floor plans, price history
  • Favorites, saved searches + alerts
  • Lead / enquiry capture & agent contact
  • Seeker & agent accounts (auth + roles)
  • Free agent listing management + lead inbox
  • Basic listing analytics

deferred Later

  • Billing / subscriptions / paid placement
  • MLS / RESO feed ingestion (v1 = CSV/API only)
  • Heavy moderation / admin plane
  • Mortgage integrations & price estimates
  • Recommendations

04 Architecture Principles

  1. Portability over lock-in — the "own Supabase" doctrine. App code depends only on open, portable primitives (Postgres wire protocol, S3 API, JWT, Redis, containers). Managed providers rent us speed in v1; the same open-source software is self-hosted at scale. Provider swap = connection string + adapter, not a rewrite.
  2. Service boundary / repository layer. App never calls a proprietary SDK directly. All data access flows through our own API layer — that layer is the backend, and becomes self-hostable.
  3. Decouple planes. The public read path (CDN + static + search) is independent of the write/back-office plane, so the marketplace stays up under partial failure.
  4. Derived data is disposable. Search index, caches, and static pages are rebuildable projections of the Postgres source of truth, kept in sync by events / on-demand revalidation.
  5. Mobile-first, tokens-only UI. Per Blueprint — no arbitrary pixel values, ≤3 type sizes per screen.

The one rule that makes it portable

Managed providers are chosen for their open primitives underneath — Supabase is just Postgres + GoTrue + an S3 API. We depend on the wire protocols, never the proprietary surface, so lifting to owned infra costs a config change, not a rewrite.

07 App Structure

Single Next.js app with route groups for v1 — not a monorepo.

(public)

Marketplace routes · own layout · seeker auth · SEO / ISR rendering.

(agent)

Back-office routes · own layout · agent auth · dashboard shell.

Shared components/, lib/, and a server/ data-access layer (the §04 service boundary). Monorepo split is deferred until a separate team owns the back-office or release cadences diverge — starting single doesn't foreclose it.
